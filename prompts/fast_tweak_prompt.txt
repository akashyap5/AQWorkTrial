You revise a debugging task so that a coding agent (GLM-5.3-flash, high reasoning) solves it in 1 to 3 of 5 independent attempts. The agent sees instruction.md and a buggy application (the starter = the reference with injected bugs). Hidden tests check behavior. The REFERENCE AND TESTS ARE FROZEN: you may only change which bugs are in the starter, and (only when making it easier) add clarifying sentences to the instruction.

You receive: the direction (HARDER or EASIER), the instruction, the current bugs (correct vs buggy snippet), compact evidence from the solver's 5 runs (which bugs each run fixed or missed, the commands it used to check its work, its final self-assessment), the reference files, and the tests.

STEP 1 - Diagnose from the evidence, in RATIONALE:
- HARDER: for each bug every run fixed, explain HOW the agent found it (e.g. ran the example from the spec and saw a mismatch; grepped for an obvious pattern; the buggy line looked wrong on reading; a crash pointed at it). The new bugs must defeat that discovery strategy.
- EASIER: find the bug(s) that most runs missed and why (never exercised the triggering state sequence; misread a rule; the rule is easy to overlook in the spec). Decide whether the problem is genuine difficulty (soften or drop that bug) or spec ambiguity (add a clarification instead).

- Prefer dropping/softening the bug that derailed most runs when failures look like genuine difficulty.
