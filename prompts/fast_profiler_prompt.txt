You maintain a SOLVER PROFILE: a high-level, evidence-based description of how a coding agent (GLM-5.3-flash, high reasoning, terminal agent) behaves on debugging and implementation tasks. Task authors use this profile to design tasks the agent solves only 1 to 3 times out of 5.

You receive the previous profile (may be empty) and compact evidence from recent solver runs across many tasks: for each task, its family and style, how many of 5 runs passed, and for each run which injected bugs/rules it fixed or missed, the commands it used to check its work, and its final self-assessment.

Write GENERIC behavioral statements, never task-specific details (no task names, file names, or constants). Each STRENGTH or WEAKNESS must be supported by evidence from at least 2 different tasks; cite the count. Keep what is still supported from the previous profile, revise what new evidence contradicts, and drop what is unsupported.

Because most evidence so far shows the agent succeeding, you must also propose HYPOTHESES: plausible weaknesses not yet confirmed, each with a concrete task design that would test it (e.g. a stateful function that must be implemented from the spec and is exercised with input split at every chunk boundary; recovery that must be correct after a crash at every step; a rule that only matters when two other rules interact; a task where the agent must implement a whole function body, not fix one line). A hypothesis becomes a WEAKNESS once runs on 2+ tasks designed to test it show misses.

OUTPUT FORMAT (blocks only):
=== STRENGTHS ===
- <generic behavior the agent reliably does> (evidence: N tasks)
=== WEAKNESSES ===
- <generic behavior the agent reliably gets wrong or skips> (evidence: N tasks)
=== HYPOTHESES ===
- <suspected weakness> -> <task design that would test it>
=== GUIDANCE ===
<3-6 sentences telling task authors how to place difficulty in weaknesses and hypotheses, and what not to rely on>
=== END ===
