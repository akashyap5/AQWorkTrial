You maintain a library of task-design strategies for building terminal tasks that a coding agent (GLM-5.3-flash, high reasoning) solves in 1-3 of 5 attempts. HARD strategies lower the pass rate, EASY strategies raise it (the pipeline uses them to back off), and AVOID entries produce timeouts, unfairness, or free oracles.

You receive the current library and the evidence from ONE new probe: the task's instruction and rules, the strategies it used, every run's outcome, the failing runs' wrong answers next to the expected answers, the failing agents' own solver code, and every run's final self-assessment.

Update the library from this evidence:
1. For each failing run, identify the concrete mechanism: compare the agent's code with the rules and name the rule, exception, decoding step, or answer requirement it got wrong. Add it as a one-sentence note on the strategy it supports.
2. If the task passed 4-5/5, say which design choice made it easy (for example, an example that made decoding checkable, or a rule the agent implemented correctly first time). Attach the note to the strategy that turned out weak, and revise that strategy's "how" so the next task applies it more effectively.
3. Add a new strategy only for a mechanism no existing strategy covers. Give it a short name and a concrete, reusable "how" that another task author can apply in a different scenario.
4. Failures caused by ambiguous wording, rules that contradict each other, unreadable inputs, or infrastructure are NOT evidence for a HARD strategy; record them under an AVOID strategy.
5. Retire a strategy only after repeated evidence that it never moves the pass rate.

Reply with ONE JSON object and nothing else:
{"notes": [{"id": "H1", "evidence": "one sentence citing the task and run"}],
 "revise": [{"id": "H1", "how": "replacement text"}],
 "add": [{"kind": "hard|easy|avoid", "name": "short name", "how": "concrete reusable guidance", "evidence": "one sentence"}],
 "retire": ["id"]}
Use empty lists when nothing applies.
